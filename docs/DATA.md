# Data Files

All catalogs under `data/` are pipe-delimited (`|`) flat files, one record
per line, with a leading `#`-prefixed header line documenting the field
order. They are read-only at runtime (no module writes to them). Malformed
records are skipped individually; a database exceeding its
malformed-record tolerance degrades safely to an empty catalog (logged as
`E105`) rather than crashing.

## `data/desktops.db`

Fixed catalog of the 8 Tier-1 supported desktop environments.

```
name|description|packages|startup_binary|startup_args|systemd_flag|min_ram_mb
```

- `startup_binary` is schema-validated against a fixed allowlist at load
  time (rejected otherwise) — it is never passed to a shell unvalidated.
- `startup_args` tokens are validated against a strict allowlist pattern.
- `systemd_flag` (`true`/`false`) drives the systemd-dependency warning
  shown when selecting a desktop.

## `data/proot_distros.db`

Catalog of officially supported Proot Linux distributions.

```
id|name|proot_id|architectures|priority|status|package_manager
```

- `architectures` is `all` or a comma-separated allowlist (`aarch64`,
  `x86_64`).
- `package_manager` drives per-package-manager argv construction in
  `install_proot_package()` (structured executor only — see
  `docs/SECURITY.md`).

## `data/proot_apps.db`

Catalog of apps installable inside a Proot distro.

```
id|name|category|description|install_target|architectures|proot_distros
```

- `install_target` is validated against a strict grammar at schema load
  (shell metacharacters rejected) before ever reaching the structured
  executor.
- `proot_distros` is `any` or a comma-separated allowlist restricting
  which distros the app may be installed into.

## `data/termux_apps.db`

Catalog of native Termux packages/tools.

```
id|name|category|description|package_name|install_source|post_install_note|github_repository|github_ref|github_artifact|github_sha256
```

- `install_source` is `pkg` or `github`. A `script` source is rejected at
  schema validation — never a supported install path.
- For `github` sources: `github_ref` must be a pinned tag or commit SHA
  (a branch name is rejected); `github_sha256` must be a 64-character
  lowercase hex string, verified against the downloaded artifact before
  install; any checksum mismatch aborts with no partial state.
- `package_name` is validated against a strict grammar (shell
  metacharacters rejected) at schema load.

## `data/defaults.conf`

The default persisted configuration, in `key=value` form, loaded when no
valid user configuration exists. See `docs/TROUBLESHOOTING.md` for what
happens when the active configuration fails validation, and
`docs/SECURITY.md` for the configuration grammar rules.

Keys: `config_version`, `theme`, `banner`, `banner_animation`,
`auto_launch`, `health_check_interval`, `log_level`, `check_updates`,
`language` (reserved, always `en`), `network_timeout`, `network_retries`.

## `runtime_context` (in-memory only, never a file)

`runtime_context` is built by `build_runtime_context()` (§17.4) and holds
exactly **one** key:

- `terminal_width` — detected once per launch (`COLUMNS`, falling back to
  `tput cols`, falling back to `80`) and held only in memory for the
  lifetime of the process. It drives UI mode selection (full/compact/
  minimal, §19.2) and is **re-detected every launch**.

`terminal_width` is **never persisted**: it is never written to `config`,
never written to `state`, never included in configuration exports, and
never read back from disk. `validate_config()` rejects `terminal_width`
(or any other `runtime_context` key) outright as an unknown-key violation
(D12) if one is ever found in the `config` file. There is no cache and no
stale-value scenario for this key by construction (§17.3).

## `data/reports/report.md`

Generated by `test/test_report_generator.sh` (not hand-edited). Contains a
per-file PASS/FAIL/MISSING table and aggregate assertion counts for the 18
other mandatory test files, plus an overall `RESULT: PASS`/`RESULT: FAIL`
line. Regenerated on every `bash test/test_report_generator.sh` or
`bash test/run_all.sh` run.

Because its content (including a `Generated:` timestamp) changes on every
regeneration by design, it is deliberately **excluded** from `SHA256SUMS`
(§30.2, §30.5): a checksum manifest proves a file matches a fixed value
computed once, and a file that is meant to change every run cannot carry
that guarantee without producing a false-positive integrity failure each
time the mandatory test suite is executed. All other repository files
(source, modules, the four `data/*.db` catalogs, `data/defaults.conf`,
docs) are static release payload and remain covered by `SHA256SUMS`.

## Runtime-only files (never part of the repository)

`~/.config/devils-minios/config`, `state`, and `state.bak` are written at
runtime into the user's own profile — they are user-profile artifacts, not
repository files, and are preserved across an uninstall.
